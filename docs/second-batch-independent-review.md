## P1：迟到创建响应清除下一项新研究的同名附件

### 复现过程

1. 新研究 A 选择 `same-name.txt`，填写文字并发送。
2. 服务端已完成 A 的创建，测试代理暂缓把该真实响应交给浏览器，模拟网络迟到。
3. 用户点击“新研究”，为 B 填写另一段文字，并选择同名、内容不同的 `same-name.txt`。
4. 放行 A 的创建响应，等待其回调执行。
5. B 的文字仍在，但文件草稿元信息已被清除。刷新后没有重新选择文件的提醒；直接发送 B 时创建和回答均正常，但 B 项目论文列表为空。

这是已选择但尚未上传的本地附件丢失，不是服务器已保存论文被删除。触发需要旧创建响应晚到和同名文件，正常单次上传路径不受此结论影响。

### 实现依据

- `web/static/conversation-home.js:545`：选择文件时以文件名相同为条件复用旧元信息，不能区分同名的新一次选择。
- `web/static/conversation-home.js:597`：旧创建回调通过元信息 JSON 相等判定可以清除原草稿。A、B 共享未建项目的草稿槽位，只有文件名的元信息相等。
- `uploadSelected` 在缺少元信息时直接返回，未把仍在内存的 B 文件作为需要恢复或提示的异常，因此用户继续发送时静默漏传。

### 签收前的修复要求

1. 每次附件选择或草稿具有独立身份/版本；不要仅凭名称或相同元信息判断它属于旧请求。
2. 旧创建回调仅转移、清除该请求实际持有的附件快照，保护后来新研究的文件及文字；A 的已授权操作仍可在自身项目完成。
3. 内存文件与元信息不一致时应恢复一致状态或明确提示，不能静默按“没有附件”发送。
4. 增补针对同名不同内容、重新选择、移除再选择、刷新恢复及迟到响应的回归，核对 A/B 各自资料的内容和数量。保留已有上传幂等、笔记保护及七条主路径验证。

完成这处收尾并复测后再决定签收第二批；本次不要求扩大到第三批内容质量或全面 UI 重构。
