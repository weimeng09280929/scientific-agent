## P1：达到请求总调用上限后仍提供无效的原请求重试

依据：`core/invocation_audit.py:41,119`，`core/workspace/conversations.py:1076,1125`，`web/static/conversation-home.js:315`。

普通对话 AuditScope 默认允许同一 operation/group 累计 6 次模型网络尝试；显式重试复用原请求 ID，也继续累计同一预算。Provider 默认一次调用最多 4 次网络尝试（初次加 3 次自动重试）。累计上限本身合理，但达到上限后服务把原因转换为一般失败提示，界面继续显示“重试此消息”。

通过实际会话 API + SDK MockTransport 复现：

1. 初次模拟连接失败：实际进入替身传输层 4 次，消息失败。
2. 用户明确重试：再进入传输层 2 次，达到 6 次累计上限，消息失败。
3. 将替身切换为可正常回答，再次明确重试：进入传输层 0 次，仍失败；界面对应的错误仍建议查看记录后明确重试。
4. 用户消息仍只有一条，未丢数据。问题是恢复路径无法生效，而非去重失效。

这不是对既有真实 v2 失败根因的重新判断；该验收还有专用总预算，不能混为一谈。

建议：保留总预算保护，但返回结构化失败原因、是否可重试、剩余尝试或冷却信息。预算已用完时停止提供同义无效重试，给出明确的新一轮尝试/重新提交入口；关联原请求及原方案、说明额外调用，不能暗中清零或移除限额。针对暂时网络失败、限流、鉴权、预算耗尽分别给出恢复方式。

## P1：真实引文存在不等于“用户提供”标签正确

依据：`core/workspace/plans.py:287`；真实方案 `docs/real-guided-user-experience/adopted-research-plan.md:99,141`。

方案的 user 陈述只检查 quote 非空并存在于用户上下文。正文 text 是否与引文一致，未得到同等约束。结构化 conditions 的 value/quote 有更严格校验，但不能覆盖 sections 正文。

离线探针：用户已声明“只有CPU，没有GPU”，陈述附上这一真实 quote，正文却写“用户已确认有GPU可供使用”。在方法专属字段未出现 GPU 冲突时，`validate_plan` 接受了该方案。此探针只确认该校验函数的缺口，没有把伪造方案采纳到任何真实项目。

真实文件存在较温和但相关的混写：标为“用户提供”的稳定性陈述加入“建议 3–5 个”种子；标为“用户提供”的四周期限陈述加入“小规模仿真脚本准备”的安排，而引文只有“四周”。原修订意见也要求去掉脚本/冒烟测试交付，但修订未完成。

建议：把用户明确事实、模型建议、由文献推导的解释拆成独立陈述；对资源、数值、否定等可确定冲突增加校验。不能仅依靠提示词或引用存在性宣称依据成立；自动检查仍无法全面证明语义和科学正确性。新增相反含义引文、混入额外数量/任务的反例。不要删除已有引用和条件校验。

## P2：研究现状导出缺少独立核对来源的完整映射

依据：`core/research_tasks/synthesis.py:238` 和真实下载的 `research-status-report.md`。

报告的代表性工作、方法关系主要使用 `cand-…` 内部 ID，当前 Markdown 渲染没有在报告内附上这些 ID 到题名、作者、年份、DOI/URL 的完整对照。另有 public-source-catalog 文件不能替代单份报告自身的可追溯性。注意：正式方案导出已经有题名与 DOI，本问题不应描述为所有导出都完全没有来源。

建议用稳定的 [1]、[2] 等可读编号，并在每个可独立下载的版本附参考文献表、来源链接与阅读范围；编号绑定该版本快照。内部 ID 保留在机器元数据或审计附件，不能简单全局替换损坏关联。

## P2：研究现状交付仍以运行记录为主体

依据：`core/research_tasks/service.py:1101` 及真实对话的检索交付消息。

交付正文主要是查询串、来源数量、纳入数量、上限及提示，用户仍需再次提问才获得研究上的解释。默认引用列表又由全部新保存/关联条目生成（同文件 1018 行），应继续区分候选目录、纳入分析和实际用于陈述的文献。

建议先呈现少量有依据的研究要点、关键差异/不确定性和下一步选择；将完整查询与计数折叠到任务详情。优先复用已生成报告，不为排版额外增加模型调用，也不能把所有入库文献冒称为每条结论的依据。
