# 理工科研究方案：模板、生成与审阅（第六步 A）

本步继续使用真实入口 `/`、`/workspace` 的 `index.html`、`app.js` 和
`conversation-home.js`。不另建研究方案数据库，不迁移用户项目。
产品终点仍是 DESIGN：方案可审阅不等于实验完成、结论成立或研究结束。

## 1. 领域契约

公开目录统一为以下九项，后端、主应用和旧页面选择项一致：

| ID | 展示名称 |
| --- | --- |
| `computer_science` | 软件工程与计算机系统 |
| `ai` | AI 与机器学习 |
| `security` | 计算机安全与隐私 |
| `engineering` | 工程与技术 |
| `materials` | 材料科学 |
| `physics` | 物理学 |
| `chemistry` | 化学 |
| `energy` | 能源 |
| `mathematics` | 数学 |

领域与研究方法是两条独立轴。物理学不再被命名为“物理与理论研究”；
选择物理学不会自动选择理论研究。补齐已开放的工程、数学领域画像，
数学使用定义、假设、证明与反例的口径，不强制套用训练和准确率指标。

`cs`、`computer science`、`人工智能`、`materials science`、`math` 等别名
映射至上述稳定 ID。`stem:LLZO固态电解质` 等能识别的细分方向保留原大小写；
无法判断的方向、空细分方向、过长或含标签的输入被拒绝并要求澄清，
不自动归入计算机。旧接口的空领域仍沿用原默认值以保持兼容。

开放的是**理工科研究规划**，不是所有学科和所有操作能力。医学、临床、人体、
药物、湿实验、危险操作、具体实物设备操作指导，以及真人访谈和伦理审定
不在承诺范围内；计算机安全仅限公开数据、模拟或明确授权测试。
自定义领域和把项目标为 AI 都不能绕过检查。对明确排除临床等研究的表述
做有限的否定识别，但剩余请求仍要检查，不能通过一句“不涉及”授权后续危险要求。
这是保守的词法范围检查，不是专业安全审核。

历史项目不改领域、不删除、不批量重写；旧方案、实验和稿件继续查看、导出。
早期要求材料、化学、物理、能源一律拒绝的测试与已确认的理工科定位冲突，
已改为验证九领域开放，同时保留别名、无效输入、未知细分方向、历史兼容及
临床/人体/危险操作拒绝测试。未扩大至生物、医学、金融或所有学科。

## 2. 共同骨架与方法差异

三类方案共用九节：研究目标与明确问题；相关工作与实际引用依据；拟研究的
差异或待验证设想；研究对象、数据或材料条件；方法与技术路线；比较、验证
或论证设计；时间、资源与可行性；局限、未确认假设和待讨论事项；参考来源。

另有真正不同的 `method_details`，不只是更换标题：

| 方法 | 专属字段 |
| --- | --- |
| `computational` 计算研究 | 数据与任务、基线、公平比较条件、预算与计算条件、评估、重复性与复现 |
| `theoretical` 理论研究 | 定义、假设、待论证命题、推导路线、证明义务、反例、边界、与已有理论的关系 |
| `experimental` 实验研究设计 | 对象、变量、对照、测量、重复与误差、资源需求、专业审核事项 |

理论方案不要求训练集、准确率或代码骨架，新命题必须保留待论证状态。
实验方案只规划，不执行、不生成结果；不把没有依据的操作参数写成确定步骤。
计算方案也不强制公式—代码映射。复现、比较、小范围改进都是合法目标，
不要求每个项目宣称提出全新方法。

旧方法生成器的真实模型提示也同步去掉“每个组成必须有核心算子/公式/代码”的假设；
没有代码的理论组成不再被自动补出已映射的公式—代码表。保留旧 IO 字段以及内部
架构测试的计算示意，不批量重生成历史方法文档。新的正式方案使用本页的会话模板
与明确采纳路径，旧方法产物并不会因此自动变成新模板正式方案。

所有陈述区分 `literature`（文献依据）、`user`（用户提供）、`proposal`
（系统建议）、`unverified`（待核实）。资源、期限、预算和权限未知时必须
填写 `待确认`，而不是补数字。引用 ID 及实际摘要/片段范围随方案保留。

## 3. 生成路径和可靠性

1. 在现有会话下打开“方案生成与审阅”，明确问题和研究方法；也可自由输入请求。
   选择、展开、刷新和准备输入都不调用模型、不创建正式记录。
2. 发送明确的制定/修订请求，沿用原消息 `request_id`、持久化、并发锁、错误和
   用户触发重试机制。生成任务使用原模型路由 `design_method_formalize`，
   不新建队列，不自动交给第五步检索。
3. 服务端核对问题、修订目标、领域与项目归属。没有问题、多个问题未选择、
   问题待复核或类型不明确时先澄清，不偷偷建立或采纳问题；此时不调用模型。
   方法提示只是建议，必须由用户明确选择/表述，不根据学科强行决定。
4. 上下文包含 brief、正式问题、已确认记录、关联论文的已提供摘要/片段、
   本会话历史与本轮要求，不使用其他会话未采纳想法。读取不到的来源不补造。
5. 返回一条当前会话的结构化方案建议，先供审阅；尚无文献依据时准确显示讨论稿。
   普通聊天不能让模型自行生成方案，未使用新结构的模型方案输出也不能发布。
   老方案缺字段仍可读，不因此重新生成或重新采纳。

最小请求示例（项目和会话已存在）：

```http
POST /api/projects/{project_id}/conversations/{conversation_id}/messages
Content-Type: application/json

{
  "request_id": "plan-request-001",
  "content": "请为所选问题生成理论研究方案",
  "plan_request": {
    "method": "theoretical",
    "question_id": "existing-question-id",
    "supersedes_id": null
  }
}
```

`plan_request` 可省略；自然语言明确要求生成且明确方法时也可进入。
不确定时使用界面选择，而不是依赖自由文本识别覆盖所有表达。
相同请求重复提交复用已保存响应，不同内容复用 ID 返回 409。
模型失败保留用户消息和失败原因，不换成看似成功的规则答案。
`dry_run` 的规则讨论稿明确标记规则模式、缺失依据和待讨论字段，不伪装成模型调研。
“暂停”“不要生成”“是否需要修改”等不会仅因带有方案词汇就生成方案。

## 4. 新增字段与兼容

没有新增 SQLite 表或独立方案存储。字段嵌入原建议与 WorkItem 的 JSON：

| 字段 | 约定 |
| --- | --- |
| `ConversationSend.plan_request` | 可空；本次方法、问题和修订目标，不改变正式主线 |
| `SuggestedItem.plan` / `WorkItem.plan` | 可空；新结构化方案，旧记录默认空 |
| `SuggestedItem.supersedes_id` | 可空；明确要修订的同项目有效方案 |
| `WorkItem.plan_version` | 正式采纳时按修订链编号，新链 v1，修订链递增 |
| `plan.template_version` | 当前 `stem-plan-v1` |
| `plan.method` / `question_id` | 三选一方法和本次明确问题 |
| `plan.sections` | 九个唯一章节及陈述依据、引用 ID、依据原文 |
| `plan.conditions` | `resources/time_budget/budget/data_access` 的值与来源 |
| `plan.method_details` | 按 `type` 判别的严格方法结构 |
| `plan.unconfirmed` / `references` | 待讨论事项和实际提供的参考论文 ID |
| 工作台 `plan_reviews[item_id]` | 独立的结构/依据摘要，不是成功概率或创新评分 |

旧方案没有编号时显示“历史未标版”，不为显示而写库。
新字段为空时不改变旧请求哈希或旧材料指纹，避免升级导致历史草案凭空过期。
聊天和选择类型不增加材料版本；正式 brief、问题、方案和来源变化仍按原契约更新。
`workflow.flow.planReady` 的依赖有效性语义不变，不等于科学有效或已经证明。

## 5. 审阅、修订与明确采纳

对话及材料面板展示正文、类型、问题、修订目标、模板/正式版本、待确认事项和
待复核状态。提供修改条件、讨论某部分、请求修订、采纳和下载此版本。
“准备检索依据”只准备可编辑的检索请求，只有用户发送才交给已有第五步任务。

修订先保存为新草案，`supersedes_id` 必须对应本项目有效方案且关联同一问题。
正式采纳仍调用原接口：

```http
POST /api/projects/{project_id}/conversations/{conversation_id}/suggestions/{suggestion_id}/apply
Content-Type: application/json

{"expected_revision": 2}
```

使用返回的实际 `item_id` 去重；原事务内同时写入正式记录和已采纳标记。
重复/并发采纳返回同一记录，不新增版本。旧正文保留，旧记录按照既有修订契约
标为 `superseded`，不是覆盖或删除内容。“采用这个方案”文本本身不等于采纳。
多个候选或指代不明时先选择。

材料指纹包含 brief、问题、来源和正文片段。缺依据快照、依据已变或过期的
草案仍可查看和下载，但禁用直接采纳；强行提交返回 409，不修改版本重试。
生成期间用户更新条件时回复仍保存，`basis_changed=true`，不能覆盖新条件或直接采纳。
已有任务状态、消息失败/中断恢复和会话异步隔离机制不变。

## 6. 证据与完整性检查的边界

- 严格校验三类字段、九节完整且无重复、方法一致、问题/修订关系、引用归属；
  缺字段、畸形或截断输出失败，不将部分内容包装成可采纳方案。
- 文献事实要求引用对应的实际提供摘要/片段原文；只有标题/年份不能支撑方法、
  结果和研究空白。伪造 ID 或伪造原文不能通过。
- 用户条件需对应已提供原文。检查典型精确数字无依据、CPU/无 GPU 条件冲突、
  新命题误写已证明、预期误写已取得结果，以及不支持的具体操作。
- 服务端从已校验结构生成 Markdown 正文，模型不能另交一份矛盾正文作为方案。
- 完整性摘要指出待确认项和是否有内容依据，不产生创新性、发表概率或成功率评分。

这些是结构、归属、原文存在性及有限冲突检查，**不是语义蕴含证明、完整的物理/
数学验证器或专业安全审查**。有真实引文也不保证推断正确。可行性、证明和研究价值
仍需研究者/导师审核；真实模型输出质量需要另行授权评估。

## 7. 导出与当前版本

沿用主聊天顶部“下载当前产物”：当前正式方案默认来自服务端主线，最近生成但
未采纳的草案不会替代它。可附带当前会话，列出真实存在的草案：

```http
GET /api/projects/{project_id}/exports?conversation_id={conversation_id}
GET /api/projects/{project_id}/exports/items/{item_id}?format=md
GET /api/projects/{project_id}/conversations/{conversation_id}/suggestions/{suggestion_id}/export?format=md
```

正式记录和草案都保留项目、问题、类型、版本/未正式编号、正文、引用、待确认事项及
待复核标记。历史方法文档仍走既有产物下载，不能冒充新模板的正式方案。
跨项目/会话草案不能下载。原研究记录导出也增加类型/版本信息，旧记录仍能导出。

沿用现有 `md/docx/pdf` 转换。MD 源码、已有页面公式渲染和打印继续可用；
本步浏览器实测了 MD 下载，没有逐份视觉验收 Word/PDF 的复杂公式、长表格和分页，
不宣称已经修复全部格式问题。
