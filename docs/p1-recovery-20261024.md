## P1 A：耗尽后的有效恢复

根因：`AuditScope` 按同一 operation/group 累计模型网络尝试，原请求默认上限 6；Provider 一次执行最多初次加 3 次自动重试。会话显式 retry 沿用同一 `request_id`，额度耗尽后 `CallLimitError` 被模型异常包装为一般失败，前端只看 `status=failed` 继续显示“重试此消息”。此前仅有 HTTP 错误和文案，缺少可恢复性的服务端状态。

修改：

- `core/workspace/conversations.py` 从异常链提取稳定原因：`connection_error`、`timeout`、`rate_limited`、`authentication`、`structure_invalid`、`budget_exhausted` 等。失败原因及冷却截止点保存在原项目 SQLite 的 `sra_chat_failures`，与失败状态同事务提交。请求读取返回 `failure.reason`、`can_retry`、`retry_after_seconds`、模型网络尝试已用／上限／剩余及 `can_restart`；读取旧库不建表。普通 retry 仅在服务端允许时进入生成；额度耗尽不再增加执行尝试或调用。
- 新增 `POST …/requests/{request_id}/restart`，必须显式提交 `acknowledge_model_cost=true`。它复制原请求的研究目标、选文、方案修订目标与材料版本；材料指纹变化时要求先复核，不能沿旧依据静默重开。每个原请求**最多一个**关联新轮次；新轮次 ID 由项目／会话／原请求确定，重复点击、响应丢失后的重放只返回同一处理记录。旧请求仍是 failed，新轮次有独立审计，不再插入第二条用户消息；新回复和建议走原会话、锁、引用校验、材料指纹和采纳事务。
- `core/invocation_audit.py` 在网络尝试时保存上层 group 的限次、价格／费用上限、模型约束和失败停止策略。新轮次若源于上层 group，继续受其**持久**限制；历史上层策略无法核实时拒绝重开，不擅自给新额度。普通请求新轮次才获得一次新的本地 6 次上限；其子轮次不能再继续重开。未清除旧计数、未改变 Provider 自动重试上限或模型路由。
- `web/static/conversation-home.js` 只在 `failure.can_retry` 为真时给原请求普通重试；预算耗尽时显示调用数和明确的“重新发起本次生成”，操作前说明再次调用模型可能产生费用。刷新先核对原请求与新轮次；未查明原因时不先展示重试按钮。认证失败与限流冷却分别提示处理方式。

方案修订失败保持已采纳 v1。新轮次成功仅保存未采纳草案，原 `suggestions/{id}/apply` 明确操作才追加 v2；真实 v2 修订仍待下一轮授权验收。

## P1 B：方案陈述的依据归属

根因：旧 `validate_plan` 对章节 `basis=user` 只检查 quote 存在于用户上下文，未核对正文是否增加事实。结构化 `conditions.value/quote` 原本更严格，但不能覆盖九节的自由陈述。真实 v1 中“用户提供”段落混有建议种子数和脚本准备，说明来源存在不等于整段得到支持。

修改：`core/workspace/plans.py` 的新方案提示词要求一条 statement 只承载一种依据性质。`basis=user` 的新陈述必须是所附原话或单个事实片段的保守转述；允许有限、可核对的“没有／暂无”等同义词与归属前缀，但额外数量、期限、资源、任务安排和解释需拆为 `proposal` 或 `unverified`。无 GPU 等确定性约束也检查所有章节，不能仅改成 `proposal` 标签绕开冲突。文献 statement 若自行加入“因此／建议”等推断，需拆出单独建议。原有引用 ID、摘要／片段 quote、结构化 conditions、方法字段、采纳时依赖校验全部保留。

新规则只用于新生成／修订；旧正式方案和草案仍按原内容读取，不批量修改、重新生成或变更采纳状态。方案阅读区及完整性提示说明历史版本可能按较早规则生成。本校验是确定性归属与有限冲突保护，**不能证明所有自然语言语义蕴含或科学正确性**；保守策略也可能要求某些合理改写拆句重生成。
